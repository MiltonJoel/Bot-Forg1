# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An async Python bot that monitors forg1.com's predictions page, sizes a bet with a fractional-Kelly strategy, **places the bet on the live UI via Playwright**, and reports everything to Telegram. `PredictionPageReader.place_bet()` and `MonitoringService` really do execute bets — treat every change to that path as a change to a money path.

### The objective: points reset every 30 days (added 2026-08-20)

**forg1's points are wiped every 30 days, and the owner is aiming at a 4,500,000-point prize threshold.** This governs every sizing decision in this file and invalidates a lot of standard betting reasoning that earlier revisions were built on — read it before touching any dial.

The bankroll does not persist. Kelly sizing, drawdown minimization, and "survive long enough to be measured" all assume a bankroll that compounds indefinitely; here it is deleted on a fixed date. Points not converted into a prize by the reset are worth **zero**. So:

- **A high probability of losing is an acceptable price for a fat right tail.** The owner has said this explicitly and repeatedly, and under this constraint he is right. Do not recommend lowering aggression on drawdown grounds alone — that argument does not apply here, and it has been wrongly made to him more than once (including on 2026-08-20, recommending `STRATEGY_MAX_PCT` 25 → 10; measured against the real objective that is the *worst* setting on the table, costing ~255k of expected terminal balance under his own thesis).
- **Optimize the terminal balance distribution at the reset date**, not the geometric growth rate, and not the max drawdown. `replay.py`'s drawdown column is still the honest measure of *sizing risk*, but risk is not the objective function here.
- **The one surviving reason for restraint is the absorbing zero, not the drawdown.** Busting on day 8 forfeits 19 days of chances, which is why expected terminal balance *falls* rather than flattens as aggression rises past the optimum. "Bet everything" is still wrong; "bet cautiously" is also wrong.
- **Always establish how many days remain in the cycle before modelling anything.** The answer changes completely at 27 days versus 3.

**The 4,500,000 target is a threshold objective, and it is NOT the same optimization as "grow the bankroll".** Measured 2026-08-20 from 117,303 pts with 27 days left (~46 markets), resampling the logged markets — `P(reaching 4.5M)`:

| stake rule | P(hit) if `w=0.12` | P(hit) if `w=1.00` | median balance if `w=0.12` |
|---|---|---|---|
| Kelly at `kelly_fraction=1.0` | 1.8% | 0.0% | 833,789 |
| flat 25% of bankroll | **5.4%** | 0.1% | 437,519 |
| flat 50% | 5.3% | 0.1% | 17,727 |
| flat 75% | 3.5% | 0.1% | 459 |
| flat 100% | 0.8% | 0.1% | 0 |

**SUPERSEDED IN ITS CONCLUSION as of 2026-08-31 — forg1's `max_bet` closes the threshold branch.** Everything above about bold play and P(hit) assumed the stake could grow with the bankroll. It cannot. `max_bet` is a real per-market ceiling read straight off the RSC payload, and it **binds on 29% of bets (23 of 78 logged)** — the signature is a stake landing on an exactly round number while sitting at 7–24% of balance, i.e. Kelly asked for more and the site refused. Values seen: 10k/20k/30k/50k/100k, and **since 2026-08-22 it has been a flat 50,000 regardless of pool size** (a 9.7M pool got the same cap as a 572k one). At a 418k bankroll that is 12% of balance; at 1M it is 5%; at 2M it is 2.5% — **growth turns additive exactly when it needs to compound.**

Simulated 2026-08-31 from 418,085 pts with ~16 days left (144 markets at the *now*-observed ~9/day), resampling the logged markets, n=2500:

| `crowd_weight` | `max_bet` | world | P(hit 4.5M) | median finish |
|---|---|---|---|---|
| 0.12 | **ON** (real) | edge is real | **0.1%** | 1,407,841 |
| 0.12 | OFF (hypothetical) | edge is real | **16.7%** | 1,011,135 |
| 0.12 | ON | edge is zero | 0.0% | 29,215 |

**The cap alone moves P(hit) by 167x, and no dial in this repo touches it.** 4,500,000 is not reachable this cycle at 50,000/market whatever the strategy does, so **the live objective for the rest of the cycle is terminal balance, not the threshold**. That is not the growth-optimal reasoning this section rejected — it is that the threshold branch is closed by an external constraint. The one open lever is *how many* markets get bet, which is why the coverage bug below mattered more than any dial. If forg1 ever raises the cap, or if `max_bet` turns out to be per-*bet* rather than per-market, re-open this immediately — that is the single highest-value unknown left (check forg1's rules first; deliberately working around a stake limit is an account-closure risk, not a strategy).

Two things follow **for the pre-2026-08-31 threshold framing, kept because they are correct whenever the cap is not binding**. **Kelly is the wrong sizing rule for a threshold** — it maximizes growth rate, and flat ~25% staking is 3x better at actually reaching 4.5M despite a much worse median (Dubins–Savage: for a goal you are unlikely to reach in a fair-or-worse game, bold play beats growth-optimal play). And **boldness has an interior optimum around 25–50%** — past that you bust before the horizon and P(hit) collapses. Note the median column is only decision-relevant if sub-target points have value; if 4.5M is strictly all-or-nothing then a 833,789 finish is worth exactly as much as a 0 finish, and only the P(hit) column matters. **Establish whether there are intermediate prize tiers before optimizing** — that single fact flips the recommendation between Kelly 1.0 and flat 25%. Also note the strongest lever is not sizing at all: P(hit) scales with the number of markets bet, so stream uptime and not skipping markets matters more than any dial. **That last sentence is the one claim in this section that 2026-08-31 strengthened rather than overturned** — with the cap binding it is close to the *only* lever left.

**The market rate in this section is stale by 5x.** Every simulation above resampled "the observed 1.7/day". Measured 2026-08-31 over the last two weeks the bot sees **~9 markets/day** (8, 9, 3, 8, 7, 8, 5, 8, 10, 10, 8, 10, 9, 10). Re-derive the horizon before quoting any number above. Separately, 16 of the 34 days from 2026-07-29 to 2026-08-31 logged **zero** markets, and at least two of those gaps line up with known bot outages rather than a dark stream (the 2026-08-18 `DISPLAY` bug, the 2026-08-25 restart) — worth checking against the actual stream schedule, because on the cap-bound objective uptime is the whole game.

Production runs on a Necbeard KVM VPS (LA, 2GB RAM / 20GB SSD) under `xvfb-run` as a systemd service (`HEADLESS=false` with a virtual display — real headful Chrome is what keeps Cloudflare happy). ## Architecture

`main.py` wires everything and runs two independent asyncio tasks under `_run_forever` (crash → log → restart in 10s): `MonitoringService` and `KickLiveChecker`.

- `app/bot/browser.py` — `persistent_context()`: real Chrome (`channel="chrome"`) with an on-disk profile at `.auth/chrome-profile`. The persistent profile is what preserves the Cloudflare clearance across runs. It deliberately strips Playwright's profile-hostile default flags and refuses to launch if another Chrome holds the profile (`SingletonLock` check).
- `app/bot/login.py` — forg1 auth is via Kick OAuth and the session cookie is session-scoped, so the profile alone doesn't survive restarts: cookies are snapshotted to `.auth/forg1_state.json` after a confirmed login and re-injected on startup. First run blocks on manual login. Login state is detected from the server-embedded `"isLoggedIn"` flag, not the DOM.
- `app/bot/prediction_page.py` — all scraping. Predictions are NOT scraped from the rendered DOM: forg1 is a Next.js app and the data is parsed out of the RSC payload (`self.__next_f.push`) fetched over `page.request.get()`. Consequence: the visible DOM can be stale, so `place_bet()` reloads the page before clicking. Betting is a two-step UI flow whose final "Confirmar" button is Cloudflare-gated; everything after the outcome click is single-attempt (never retry a possibly-submitted bet). Balance reads/refresh DO use the rendered DOM (header selectors).
- `app/services/monitoring_service.py` — poll loop: idle/active poll intervals, a stabilization wait before betting (re-reads the prediction so the pool settles), dedupe via `.data/seen_predictions.json`, one in-memory pending slot for result reporting. **The whole loop is stream-gated** (`_stream_offline()`, shared with the balance refresh): off-stream forg1 opens no markets, so reading the page all night finds nothing and only hands Cloudflare/Vercel a steady automated pattern. The gate is "confirmed offline", not "not live" — `KickLiveChecker` keeps its last known state when a check fails or is blocked, so a Kick outage never blinds the bot to a live market. A non-empty `_pending` slot overrides the gate, or a bet placed just before the stream ended would never get its result reported.
- `app/strategies/` — pure decision logic (`decide(Prediction) -> BetDecision`); strategies never see a Page. `ContrarianPariMutuelStrategy` is the one in use. Forg1 is pari-mutuel, so an outcome's pool share IS its price (share `s` pays `1/s - 1`) and backing favourites has zero edge by construction. It shrinks the crowd share toward uniform via `STRATEGY_CROWD_WEIGHT`, blends Valve's ratings for ranked head-to-heads, and stakes the growth-optimal amount. `STRATEGY_UNRATED_CROWD_WEIGHT` is a second dial for markets with no official rating (kill counts, player names, one-off questions) because the calibration was measured on CS2 maps ONLY — applying it elsewhere is an assumption, not a measurement. `BANKROLL_STOP_PCT` is the backstop. **Do not quietly lower the aggression** — raise `STRATEGY_UNRATED_CROWD_WEIGHT` alone if non-team markets need calming.
- **Both crowd weights moved 0.12 → 0.85 on 2026-08-31, on the owner's instruction to "make every change that gets me closer to my goals", after being shown the case below.** The measurement: over **86 logged head-to-heads** the crowd implied the favourite wins **67.8%** and the favourite actually won **65.1%** (56/86). The pool is close to calibrated. The 0.12 that shipped for two weeks was measured at **n=19** and did not survive the sample growing; the running estimate has gone 0.12 (n=19) → 0.67 (n=25) → 1.00 (n=36) → 0.85 (n=86), and those samples are nested, but 86 is no longer a number this file can wave away. The book agrees: **our picks won 29.5% (23/78) and the prices we actually took needed 28.5% to break even** — dead level. Realized ROI +16.4%, bootstrap 95% CI **[-35.4%, +79.8%]**, P(true ROI ≤ 0) = **29%**.
- **Why this is NOT the prohibited argument.** The rule above bans lowering aggression *on drawdown grounds*. This is expected-terminal-balance, which is the objective this file names, and 0.85 wins it **in both worlds**: simulated from 418,085 over 144 markets, median finish **1,870,487 vs 0.12's 1,407,841** if the contrarian edge is real, and **225,275 vs 29,215** if it is not. Mean likewise (1,922k vs 1,454k; 332k vs 267k). It costs nothing on the threshold either — P(hit 4.5M) is 0.1% at both, because the `max_bet` cap decides that, not this dial. There is no configuration tested in which 0.12 finishes ahead. It is also **not "stop betting"**: at 0.85 the strategy still places 80 bets per 144 markets against 0.12's 95.
- **The mechanism is self-dilution, and it is the real house edge here.** forg1 takes **zero rake** — verified on all 121 logged markets, `pool == sum(outcome points)` exactly, max abs difference 0 — so a bet struck at the *pre-bet* price is exactly fair. What makes it unfair is our own stake joining the side we back. Measured over the 78 logged bets: mean fair odds **4.32x** against mean odds actually obtained **3.29x**, i.e. **-23.9% of the price given away**. Stake-weighted, if the crowd price is the truth, that is **-6.98% per unit staked = -151,959 expected** on the 2,175,865 staked, against +357,133 realized (so ~509k of luck). The damage is concentrated and stake-dependent: 60 bets staking under 10% of the side's own pool lose 3.2% of price; the 18 above that lose 14–79%. **At `w=0.12` a side holding 17% of the pool is priced at 50%, Kelly asks for an enormous stake, and that stake destroys its own price.** Fixing the probability fixes the sizing — dilution falls from -9.2% to -7.9% in simulation with no new dial. A separate "cap the stake at X% of the side's pool" guard was built and tested: it helps in the zero-edge world and hurts in the real-edge one, is strictly second-order to `w`, and was **deliberately not shipped**. Do not add it without a reason `w` cannot supply.

That reasoning was sound on the sample it had; it was n=19. Note **any weight below 1.0 mathematically favours the underdog**; it only sets how good a price is demanded, and 1.0 means "pool is a fair price" (bets almost never). `AggressiveFractionalKellyStrategy` is RETIRED (-85% bankroll on replay); do not re-enable it.

Separately, note the kill switch resets on every restart (`_bankroll_exhausted` re-references `session_start_balance`), so repeated 40% drawdowns compound across restarts — it is a session circuit breaker, not lifetime protection. **Do NOT "fix" that by persisting `session_start_balance`** (measured 2026-08-20, and the fix was proposed here before the reset constraint was known): under the 30-day reset it lowers `P(reaching either prize tier)` in every configuration tested — Kelly 1.0 goes 3.8%→3.5% at 3.6M, flat-25% staking goes 6.2%→4.5% — because stopping for the rest of the cycle forfeits every remaining chance, and the drawdown it prevents costs nothing that was not about to be wiped anyway. `BANKROLL_STOP_PCT=0`/off is the best-measured row for flat staking. The reset-on-restart behaviour is load-bearing for the real objective; treat it as a feature until the points stop resetting.

- **Team/Team/OT map markets** are the one exemption to `STRATEGY_MAX_OUTCOMES=2`. Forg1's map questions sometimes carry a third option, `OT`, which wins the market outright — both team bets lose when the map goes to overtime. Do NOT "fix" this by just raising the outcome limit: shrinking OT toward a 1/3 uniform prior prices an 18%-share side (measured: 18.3% and 20.4% in the two logged markets) at ~31% against a 4.5x payout, i.e. a fake **+0.7 edge** that would stake the cap on overtime every single map. The Valve rating blend now runs on that inner head-to-head, so ranked teams still get it. Lowering the weight makes OT bettable, which is a bet that CS2 maps reach overtime more often than the crowd pays for.

- `app/utils/http.py` — IPv4-first `urlopen`, used by the notifier and Kick checker. It REORDERS addresses (IPv4 first, IPv6 kept last) and tries every one. ## The Turnstile confirm gate

The final "Confirmar" button in the bet modal is Cloudflare-Turnstile-gated and **fails on roughly a quarter of attempts at random** — 8 of 34 in the logs, spread across dates and predating any recent change. Diagnostics captured it as a plain `disabled: True` on the `<button>` for the whole wait, with no aria-disabled and no overlay: the site simply never enables it. Stake size is NOT the cause — placed bets range up to 14,980 while failures start at 3,675, so the two ranges overlap completely.

**Confirmed live 2026-07-31**: on a failure the dialog contains `iframe[src*="challenges.cloudflare.com"]/turnstile/...` and the `CONFIRMAR` button is `disabled: True` while `CANCELAR`/`Close` are enabled. The hidden `cf-turnstile-response` field is what the site watches; while it is empty the button stays disabled. So the gate is Turnstile failing to issue a token, not the button or the click.

Best current explanation: Cloudflare serves Turnstile in two modes at random. Non-interactive solves itself and the button enables (every bet that has ever worked); **MANAGED renders a checkbox in a cross-origin iframe and waits for a real click**, which nothing was doing — so `disabled` stayed true until timeout. `_clear_turnstile_then_click` polls on a 0.5s interval, ticking the checkbox and retrying the button each round.

**Confirmed on the VPS 2026-08-12, and the mitigation was dead code.** A failure logged the Turnstile frame present, `CONFIRMAR disabled: True`, `Turnstile token: EMPTY` — and *not one line* from `_tick_turnstile_checkbox` across 27s of polling (~54 rounds). The widget was looked up with `page.locator('iframe[src*="challenges.cloudflare.com"]')`, which only queries the **main frame's** document; the frame is nested deeper, so `count()` was 0 every round and nothing was ever clicked. `page.frames` (which `_log_confirm_failure` already used, two lines later, successfully) is the lookup that works — hence `_turnstile_frame()`, now shared by both. The checkbox is also unreachable behind its shadow root, so the real click lands on `frame.frame_element()`. Do not go back to a main-frame iframe selector; the fake in `tests/test_place_bet_flow.py` models the nesting and goes red if you do.

**Answered 2026-08-12 18:00 UTC: clicking does NOT earn a token.** The clicks fired ("Clicked the Turnstile widget directly (attempt 2)") and the token was still EMPTY. The widget URL on that failure ended `/dark/fbE/failure_retry/normal` — Turnstile encodes its state there, and `failure_retry` (vs `new`) means the challenge had already **errored**, so it was never waiting on a human and clicking it was dead effort. `_tick_turnstile_checkbox` now logs the widget's untouched state on first sight and, when it sees that marker, calls `window.turnstile.reset()` once per bet (the documented remedy) instead of clicking a corpse.

**Untested against a real failure as of 2026-08-12** — the gate only fires on ~25% of bets, so it needs live confirmation. What to grep after the next one: `grep -E "untouched state|asked the widget to reset|Turnstile token" logs/forg1_monitor.log`. If the widget arrives as `new` and only turns to `failure_retry` after our click, the click itself is the trigger and the fix is a humanized pointer move before clicking. If it arrives already `failure_retry` and the token is still EMPTY after the reset, the gate is IP reputation — the same datacenter-IP verdict that blocks Kick's player API (see the Kick viewer note) — and the only lever is a residential IP. Do not resume tuning clicks either way.

Ruled out by measurement, do not re-investigate: **stake size** (placed bets reach 14,980, failures start at 3,675 — ranges overlap) and **the Kick tab stealing focus** (open during all 23 successes AND all 7 failures).

**A "failed" confirm does NOT mean the bet was not placed.** Checked against forg1's own bet history: 3,675 and 4,275 both appear there as real settled bets, and both were logged here as "Final confirmation did not appear". The button reads `disabled` **because the bet already went through**. A retry loop briefly lived in `place_bet` on the opposite assumption — it would have staked twice. `place_bet` is single-attempt past the outcome click and `_ConfirmResult` has only PLACED (summary rendered, certain) and UNKNOWN. The Telegram message says "may have gone through, check before betting manually" rather than "failed". Do not re-add a retry without a way to positively verify no bet exists.

## The stake field must be read back

`fill()` sets a value and fires ONE `input` event. React's controlled number input does not always pick that up, and when it misses, the component keeps its own state — the site's default, which is `min_bet` (500). The bot would then confirm a 500-point bet while the log said 6,331: **the wrong amount, silently, on a money path**, and the logs would never show it because they record the intended figure. `_fill_amount` now reads the field back, retypes key-by-key (`press_sequentially`, which fires per-keystroke events React cannot miss) if it disagrees, and raises `_AmountNotAccepted` rather than confirming a stake it could not verify. Never remove that read-back.

## Secrets in logs

**Never log a caught exception directly** — use `short_error(exc)` from `app/utils/retry.py` at every site. Playwright errors embed a full "Call log" containing the request headers, and those headers carry `forg1_session`, the actual login cookie. `logger.error("... ({})", exc)` in the monitor's read handler wrote live session cookies into `logs/forg1_monitor.log` (278 occurrences before this was caught) and into a Telegram outage alert. `short_error` takes the first line — which holds the whole diagnosis — and redacts anything cookie-shaped as a backstop.

## Remote control

`/reainiciobot` (also `/reiniciobot`, `/reiniciarbot`, bare or slashed) sent to the bot's Telegram chat tears down the browser session and relaunches it: fresh Chrome, fresh login from saved cookies, any stuck modal or wedged tab gone. Handled by `TelegramCommandListener`, which only honours messages from the configured `TELEGRAM_CHAT_ID` — the token is a shared secret in `.env`, so the chat check is the actual authorization. It also skips the backlog on startup, or a command sent hours earlier would restart-loop a systemd-managed bot.

**The token is shared with OpenClaw.** `getMyCommands` on `@forg1_bot` returns ~60 OpenClaw commands including `/reset` ("Reset the current session") and `/restart` ("Restart OpenClaw") — which is why this bot must NOT use those names, and why the "something went wrong while processing your request" replies in Telegram come from OpenClaw, not from here. Both programs polling `getUpdates` on one token also race: whoever polls first consumes the update, so commands go missing at random and Telegram can return 409 Conflict (logged once, explicitly). The real fix is a dedicated token from @BotFather for the betting bot.

## Desktop autostart (systemd --user)

`forg1.service` runs headful (`HEADLESS=false`), so it needs the session's `DISPLAY`. It used to be `WantedBy=default.target` — and in the **user** manager, default.target is reached when the manager starts, *before* GNOME login imports `DISPLAY`. `After=graphical-session.target` does not save you there. On 2026-08-18 that meant every boot launched the bot with no display: Chrome died on `Missing X server or $DISPLAY`, `_run_forever` relaunched it 15s later, and it spun 32 launches in 11 minutes at load 12. Now `WantedBy=`/`Requisite=graphical-session.target`, and `run.sh` refuses to start headful with no `DISPLAY` so a future variant of this costs a cheap systemd retry instead of a Chrome launch. Not `xvfb-run` here (that is the VPS's answer) — on the desktop the visible Chrome window is how manual re-login happens.
